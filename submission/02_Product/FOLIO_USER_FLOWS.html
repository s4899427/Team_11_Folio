Curation

Checks before an Edition goes live

Yes, verify before publishing, in four layers. Only the first two can block a publish. The lookups and the agent give the curator a flag, never a verdict, and the curator stays accountable for every pick. Nothing is published or rejected on an agent's say-so.

1 Rules in codeHard rules, no AI. Exact 80/20 counts, outside-Australia music rejected, Edition date and city, liner note and source link present.
2 Link checkThe URL loads. Domains we trust (official sites, news, Wikipedia, MusicBrainz) pass; unknown domains are flagged for the curator to confirm.
3 LookupsArtist found in MusicBrainz with an Australian area. Gig found in Ticketmaster for that city and date. Not found does not mean fake, because small gigs are often missing.
4 Agent read (narrow job)Runs on every pick, but only answers one question: is the source real, and does the page mention the artist, venue or fact? Choosing and curating stays fully human. Advisory only. Log it in docs/AI_USE.md with the prompt, since the course requires it.
The API keys must live on the server (a Supabase Edge Function), never in the browser, and results should be cached so we stay inside the rate limits below.

Decisions

Decided and still open

  • Decided: the agent only checks that a pick's source is real and mentions the artist or fact. It runs on every pick. Picking and curating is human work.
  • Decided: the consent script says the app can ask for location, and that an artist sees a fan's name when the fan connects.
  • Decided: gig entry means someone raises an upcoming gig (name, venue, date, source link). Curators and artists can both submit. A Folio team member verifies the gig is legitimate before it shows in Browse under Nearby events. See the gig flow below.
  • Proposed: readers see only the source link on each pick, not a "checked" badge, until we test in evaluation what a badge makes people assume.
